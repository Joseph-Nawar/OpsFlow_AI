# Phase 9 M9C — Odoo Trusted-Data + Idempotent ERP Adapter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. This repository requires a single implementer; do not use subagents.

**Goal:** Implement the approved Odoo 19 Community JSON-2 trusted-data and sales-order integration, and connect it to the existing M9B order-sync coordinator without changing M9B's durable state, claim, lease, retry, receipt, or deadline architecture.

**Architecture:** One configured `OdooERPAdapter` implements the existing `BusinessDataProvider` contract and the existing `OrderSyncStepExecutor` seam. It reads the current approved OpsFlow order in a short session, closes that session before provider I/O, and performs Odoo reads/writes over bounded JSON-2 calls. A tiny Odoo addon places an immutable unique `opsflow_order_id` on `sale.order` and implements one atomic lookup/create/confirm method. Odoo's unique database constraint plus replay of the same OpsFlow UUID converges after timeout or a lost response. The M9B coordinator remains the only owner of local checkpoints, fencing, retry accounting, receipt persistence, and completion.

**Tech Stack:** Python 3.12, FastAPI, Pydantic v2 settings, SQLAlchemy 2 async, PostgreSQL, HTTPX async, existing trusted-business-data/validation contracts, Odoo 19 Community, JSON-2, pytest, Ruff, mypy, and the repository's Docker-based local workflow.

**Spec:** [Approved Phase 9 design](../specs/2026-09-29-phase-9-erp-crm-integrations-design.md), especially Sections 3–6, 10–14, 16–19. Reuse the [M9B durable sync plan](2026-09-30-phase-9-durable-sync-state-claiming-recovery.md), [system overview](../../architecture/system-overview.md), [domain model](../../architecture/domain-model.md), [roadmap](../../roadmap/project-roadmap.md), and [development guide](../../development/development-guide.md).

## Global Constraints

- Python owns provider calls, credentials, trusted-data interpretation, deterministic preflight, local persistence, and business correctness. n8n remains orchestration/scheduling only.
- M9C plugs into the committed M9B `OrderSyncStepExecutor` and `execute_next_order_sync` path. Do not modify the M9B table, claim query, lease/fencing rules, retry generations, execute-next endpoint, total deadline, or receipt semantics.
- Preserve the single `order_syncs` row and the two Odoo checkpoints: `ODOO_LOOKUP` and `ODOO_BRIDGE`. The M9B coordinator records `in_flight_step` before executor work, invokes the executor outside DB transactions, and durably writes `OdooOrderReceipt` before progressing.
- A timeout, connection loss, cancellation, or process crash around the bridge is an uncertain outcome. Retain `ODOO_BRIDGE` as the in-flight step and later invoke the same bridge with the same canonical OpsFlow UUID. Never use search-then-create from Python or blindly create a new order after uncertainty.
- Do not make exactly-once claims. Calls are at-least-once; the intended invariant is at most one logical confirmed Odoo sales order per OpsFlow order.
- Use `res.partner.ref`, `product.product.default_code`, `product.product.lst_price`, `product.product.free_qty`, and an explicit company/warehouse context. Variant `lst_price` includes normal template `list_price` plus variant `price_extra` semantics; do not calculate a substitute price in Python.
- Preserve the one-company, one-currency, rule-free base/default pricelist, same-UoM-only demo. The configured pricelist establishes normal Sales setup and matching currency; line `price_unit` is the approved OpsFlow `submitted_price`. Do not add dynamic/customer-specific pricelist evaluation, UoM conversion, or currency conversion.
- `ODOO_LOOKUP` runs the existing deterministic approved-order preflight. Before a new external order is created, the bridge transaction performs a narrow final recheck of customer/product identity and eligibility, company/pricelist/currency relationship, same-UoM assumption, variant `lst_price`, and scoped `free_qty`. The bridge first reconciles an existing `opsflow_order_id`, so a successful remote order can still be receipted after a later stock or catalogue change. A failed new-order preflight creates no external order and never rewrites the approved OpsFlow snapshot. Stock remains a live snapshot, not a reservation guarantee.
- Reuse the existing price policy: `abs(submitted_price - catalogue_price) <= abs(catalogue_price) * ValidationPolicy.price_tolerance_fraction`; current composition sets that field to `Decimal("0.05")`. Do not add another independent `0.05` constant. Trusted catalogue price is `product.product.lst_price`; the bridge writes the approved `submitted_price` explicitly to `sale.order.line.price_unit`.
- OpsFlow quantities are interpreted in the matched Odoo product variant's configured/base Sales UoM. M9C performs no UoM conversion. Preflight and the final bridge check fail closed if the actual product `uom_id` does not match that same-UoM assumption; replay comparison includes the stable Odoo `uom_id`.
- M9B remains the sole owner of the absolute 210-second monotonic execution deadline and its receipt-persistence reserve. Its existing wrapper around the entire `OrderSyncStepExecutor.execute(order_id, step)` invocation is the aggregate bound for every adapter sub-call; preserve the `execute(order_id, step)` interface and M9B deadline implementation unchanged.
- Each HTTPX request uses a finite timeout no greater than the approved Odoo per-step cap (20 seconds). M9C adds no hidden retries or sleeps and never gives each sub-call a fresh coordinator budget. M9B cancellation during uncertain bridge work causes resource cleanup, cancellation propagation, bounded uncertain/retry handling, and later replay with the same OpsFlow UUID. Preserve the five-minute lease and M9B's reserved durable-receipt path unchanged.
- `OdooERPAdapter` may only return the bounded existing `OrderSyncFailureCode` values. Never persist or return raw Odoo bodies, credentials, stack traces, or provider diagnostics.
- No provider network access or uncontrolled provider writes in the default automated suite. Any real Odoo verification uses only the explicitly designated disposable local Community database and synthetic records.
- Keep mandatory development cost at `$0`; use local Odoo Community. Do not require Odoo Online or a paid service.
- Do not add an OpsFlow Alembic migration, second sync state machine, worker, queue, retry system, orchestration API, generic ERP framework, or M9D–M9F implementation.

## Review Focus

1. An approved order's immutable OpsFlow identity and submitted values, not AI output or current provider values, determine the bridge payload.
2. Every remote mutation uses the canonical OpsFlow UUID; matching replay returns the same confirmed order, mismatched payload/state fails safely, and unique-key races reconcile by a fresh call with that same UUID.
3. A confirmed remote order is not considered locally complete until the existing M9B coordinator persists its bounded Odoo ID/name receipt under the live fencing token.
4. Provider I/O holds no OpsFlow transaction open; timeout/cancellation leaves the durable M9B step recoverable and cannot change the stable external identity.
5. `free_qty`, variant `lst_price`, configured company/warehouse, rule-free pricelist, same UoM, and submitted line price are exercised as distinct contract assertions.
6. Missing Odoo configuration leaves the existing endpoint fail-closed before claim selection; partial configuration cannot silently construct an executor.
7. No M9D CRM behavior, M9E workflow/E2E, or M9F audit work appears in code or docs.

## Interfaces and Data Flow

1. An authenticated existing `POST /v1/orchestration/order-sync/execute-next` call enters the unchanged M9B coordinator. If no complete Odoo executor is configured, it returns the existing bounded 503 before claiming or mutating work.
2. M9B claims one approved intent, performs `APPROVED → SYNCING` if needed, and commits the lease. It writes and commits the selected in-flight checkpoint before calling the executor.
3. The adapter opens a short read session for the `PersistedOrder`, closes it, and then calls Odoo JSON-2 outside any OpsFlow transaction. It accepts only orders in the coordinator's syncable state and derives all identity, PO/date, SKU, quantity, approved submitted price, and currency from the current immutable approved snapshot.
4. `ODOO_LOOKUP` obtains exact trusted customer/product and scoped inventory/prices through `BusinessDataProvider`, maps them to existing `TrustedBusinessData` records, and runs deterministic approved-order preflight. It returns no receipt; M9B moves to `ODOO_BRIDGE` only after successful lookup.
5. `ODOO_BRIDGE` loads the current immutable approved order and invokes the one fixed Odoo bridge method with the same canonical order UUID and approved payload. The method first reconciles an existing identity and compares its stored order; if absent, it performs its narrow final trusted-data recheck, creates and confirms the order in one transaction, then returns the bounded receipt. It does not repeat a Python stock gate before replay, which could incorrectly prevent recovery after the confirmed order itself consumed stock.
6. The adapter validates the bounded bridge result and returns the existing `OdooOrderReceipt`. It never writes `order_syncs`. M9B validates the claim token, persists the receipt, clears the completed checkpoint, and only then considers the next step.
7. M9C does not implement HubSpot. When the existing coordinator reaches a CRM step while only the Odoo executor is configured, return bounded `INTEGRATION_CONFIG`; M9B preserves the Odoo receipt and moves the order to its existing retryable review path. This is a temporary milestone boundary, not new lifecycle behavior. M9D later supplies the CRM step behavior behind the same executor seam.

The existing `BusinessDataProvider` request is `BusinessDataLookupRequest(customer_reference, customer_name, skus)` and the adapter returns existing `TrustedBusinessData`/`TrustedCustomer`/`TrustedProduct`. Do not persist Odoo customer or product IDs as new OpsFlow state. The M9B Odoo receipt remains only the sale-order integer ID and bounded name.

| Exact customer absent/archived/ambiguous | `TRUSTED_CUSTOMER_MISSING` / `TRUSTED_CUSTOMER_AMBIGUOUS` | No write; existing operator correction/Retry path. |
| SKU absent, archived, unsellable, wrong UoM/currency, price no longer allowed | `TRUSTED_PRODUCT_MISSING` / `TRUSTED_PRODUCT_CHANGED` | No write; preserve approved snapshot and require correction/review. |
| Current `free_qty` below approved quantity | `INVENTORY_INSUFFICIENT` | No write; existing bounded review/retry path. |
| Missing API access, addon, company/warehouse/pricelist setup or permission | `INTEGRATION_CONFIG` | No raw provider detail; operator fixes configuration. |
| Network loss, timeout, 5xx, or bridge response lost after commit | `PROVIDER_UNAVAILABLE` | M9B retains `ODOO_BRIDGE`; later attempt calls the same UUID and retrieves the existing receipt before any new-order check. No adapter retry/sleep. |
| Odoo 429 with a valid documented `Retry-After` | `PROVIDER_RATE_LIMIT` plus existing retry delay | M9B applies existing backoff; do not add Odoo-local retries. If actual Odoo response semantics are not verified, do not assume this case. |
| Malformed success shape | `PROVIDER_INVALID_RESPONSE` | No local receipt; preserve uncertain bridge step and reconcile with the same UUID. |
| Provider rejects a validly formed request for a business/setup reason | `PROVIDER_REJECTED` | Existing bounded operator correction/retry path. |
| Existing matching UUID/payload and confirmed state | Return ordinary `OdooOrderReceipt` | M9B persists the existing external receipt; bridge does not re-run stock as a reservation/eligibility gate for this replay. |
| Existing UUID with different immutable payload or unsupported external state | `IDEMPOTENCY_CONFLICT` or `RECONCILIATION_REQUIRED` | Never create a replacement identity/order; follow existing final/review policy. |
| Provider returns authentication/permission denial or the fixed bridge is absent | `INTEGRATION_CONFIG` | Bounded setup failure; never expose response body or traceback. |
| Bridge's final customer/product/company/pricelist/currency/UoM/price check fails | Existing `TRUSTED_CUSTOMER_MISSING`, `TRUSTED_CUSTOMER_AMBIGUOUS`, `TRUSTED_PRODUCT_MISSING`, `TRUSTED_PRODUCT_CHANGED`, `INVENTORY_INSUFFICIENT`, or `INTEGRATION_CONFIG` as applicable | Abort before create; preserve the approved OpsFlow snapshot. |
| Bridge returns a bounded mismatch/reconciliation envelope | `IDEMPOTENCY_CONFLICT` / `RECONCILIATION_REQUIRED` | Persist only the existing bounded M9B code; no provider details. |

No new domain state, persisted sync field, retry counter, or `OrderSyncStepExecutor` parameter is introduced. Database writes for checkpoints/receipts remain short M9B transactions. Provider reads and the atomic Odoo bridge call occur outside OpsFlow transactions. The M9B 210-second monotonic deadline is the single aggregate cap for the full executor invocation; finite HTTPX request timeouts are local defensive caps only. Its five-second receipt-persistence allowance remains intact. A timeout/cancellation after Odoo may have committed is deliberately treated as uncertain; only a confirmed same-identity bridge receipt can advance the durable local checkpoint.

## Odoo Facts and Live Setup Gates

**Already authoritative for planning:** M9A's disposable `odoo:19.0` Community probe verified Odoo 19 server `19.0-20260926`, general JSON-2 `POST /json/2/<model>/<method>` and bearer API-key direction, standard models and tested standard create/confirm behavior, stable `sale.order.id`/`name`, `free_qty` semantics, company/warehouse context direction, and variant `lst_price` semantics. These facts support the plan; they are not proof that the selected M9C development database has identical installed modules, fields, permissions, company setup, or addon behavior.

**Must be verified before freezing/using live configuration:** the target Odoo database/version and JSON-2 access; exact `fields_get` metadata and model ACLs; API-key user scope; selected company/warehouse/pricelist/currency/UoM; no price rules; exact bridge method visibility and argument/receipt shape; actual confirmation side effects; uniqueness and concurrency behavior; and timeout/connection-loss replay. Each gate is checked first with safe metadata/read-only calls, then synthetic writes only against the disposable local test database. No Odoo Online requirement or production credential is assumed.

## Complexity Review

The only new application provider is `OdooERPAdapter`; it directly satisfies two existing narrow contracts and owns one Odoo transport/configuration boundary. Its one private frozen `_OdooLookupSnapshot` is necessary because existing `TrustedCustomer`/`TrustedProduct` contracts omit provider record and UoM IDs needed only by the bridge; it does not alter shared contracts or persist new state. The only Odoo addon responsibility is the unique OpsFlow identity and atomic bridge method required to prevent duplicate logical orders. The only validation addition is a pure reuse/extraction of the already-approved deterministic trusted-data rules for a live approved-order preflight. HTTPX is reused from the lockfile and promoted to runtime rather than adding an SDK. No new provider registry, retry framework, executor wrapper hierarchy, generic ERP abstraction, worker, or distributed transaction mechanism is justified.
