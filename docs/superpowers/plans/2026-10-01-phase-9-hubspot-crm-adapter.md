# Phase 9 M9D — HubSpot CRM Adapter & Partial-Success Recovery Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. The repository requires a single implementer; do not use subagents.

**Goal:** Add the approved narrow HubSpot Company, Deal, and Deal-to-Company integration behind the existing M9B coordinator, with durable receipts only for confirmed provider success and safe recovery from partial or uncertain outcomes.

**Architecture:** One `HubSpotCRMAdapter` owns the Python-only HubSpot HTTP boundary and returns the existing bounded M9B receipt/failure contracts. A fixed `Phase9OrderSyncExecutor` dispatches the already-existing Odoo steps to `OdooERPAdapter` and the three CRM steps to the HubSpot adapter; it is a small composition point for the existing executor protocol, not a provider registry. M9B remains the only owner of claims, checkpoints, fencing, retries, receipts, and order state.

**Tech Stack:** Python 3.12, FastAPI, Pydantic v2 settings, SQLAlchemy 2 async, PostgreSQL, HTTPX, existing M9B/M9C contracts, pytest, Ruff, mypy, and a free HubSpot developer/test account.

**Spec:** [Approved Phase 9 design](../specs/2026-09-29-phase-9-erp-crm-integrations-design.md), especially Sections 3, 7–18 and the M9D milestone row. Reuse the [M9B implementation plan](2026-09-30-phase-9-durable-sync-state-claiming-recovery.md), [approved M9C implementation plan](2026-09-30-phase-9-odoo-trusted-data-idempotent-erp-adapter.md), [system overview](../../architecture/system-overview.md), [roadmap](../../roadmap/project-roadmap.md), and [development guide](../../development/development-guide.md).

## Global Constraints

- Python owns provider calls, credentials, CRM payload construction, bounded provider errors, local persistence, and business correctness; n8n remains orchestration/scheduling only.
- Keep one Company per trusted Odoo customer reference and one Deal per OpsFlow order; add no Contacts, Gmail identity promotion, custom objects, marketing, tickets, workflows, or broad CRM synchronization.
- Use Service Key authentication for the selected test account if its live capability/permissions gate passes. Target HubSpot's current date-based API generation, intending `2026-09` where the selected endpoints accept it. Never fall back to numbered v3/v4 routes merely because references disagree or lag.
- Task 1 has passed human review. It live-verified the original Company/Deal upsert routes and request shapes, association route, per-input `idProperty`, trace echo, terminal response, same-key replay, account guard, and write-response rate headers in the selected test portal. The later H1 remediation replaced runtime Deal upsert with create-only plus stage-omitting provider-ID updates. HTTP 207, 429, and nonterminal states were not induced; retain deterministic fake coverage and do not claim live evidence for them.
- A Company/Deal receipt requires confirmed terminal remote success for exactly one matching result, a confirmed opaque HubSpot ID, and no relevant item error. Async batch work requires terminal `COMPLETE`; `PENDING`, `PROCESSING`, and `CANCELED` never count as success. If Task 1 proves an operation is synchronous and its direct response contract confirms completion, document that evidence and do not add polling solely to obtain a `COMPLETE` field; if direct success is only acceptance, no receipt is allowed.
- Use only the existing M9B `OrderSyncStep`, receipt, failure-code, claim, retry, deadline, and `execute-next` contracts. Do not create another sync state machine, queue, worker, endpoint, retry loop, or CRM framework.
- Provider calls run outside OpsFlow database transactions. M9B's 210-second monotonic total deadline, 15-second HubSpot step allowance, five-minute claim lease, fencing, and receipt-persistence reserve remain authoritative; do not extend or replace them in M9D.
- The adapter performs no hidden retries or sleeps. Map `Retry-After` into the existing failure delay; M9B schedules the retry.
- Normal repository tests use fakes and make no HubSpot network calls or writes. Real account tests are explicitly opt-in and use synthetic records in the designated developer/test portal only.
- Keep mandatory development cost at `$0`. A time-limited trial is optional; if the free developer/test account lacks the required Service Key/API capability, stop and report that gate rather than making a paid account mandatory.
- Store no provider response bodies, credentials, tracebacks, or unnecessary personal data. No OpsFlow schema/migration is authorized by this plan; a provider operation handle requires a separate post-probe human approval and plan revision before implementation.

## Review Focus

1. A batch response can be accepted while its business operation is still pending. Tests must prove only terminal, uniquely matched results yield receipts.
2. HTTP 207 may contain partial success. Tests must identify the one requested item and reject errors, zero matches, or ambiguous matches without receipt.
3. A timeout or lost response can follow remote commit. Tests must prove recovery uses the same unique identity through a verified poll/status or safe replay contract.
4. A later Company, Deal, or association failure must resume from the first missing M9B receipt and must not repeat Odoo or any already receipted CRM step.
5. Missing/partial configuration, malicious error bodies, or wrong-account credentials must fail closed before external CRM mutation. Task 1 verified `GET /integrations/v1/me` and portalId 149461984; M9D must enforce the expected-portal setting before writes.

## Project-Owned Contracts

The existing executor signature remains `execute(order_id: UUID, step: OrderSyncStep) -> OrderSyncStepResult`.

- `Phase9OrderSyncExecutor.execute(...)` sends `ODOO_LOOKUP` and `ODOO_BRIDGE` to the existing `OdooERPAdapter`; it sends `HUBSPOT_COMPANY`, `HUBSPOT_DEAL`, and `HUBSPOT_ASSOCIATION` to `HubSpotCRMAdapter`. Unknown steps return the existing bounded `INTEGRATION_CONFIG` failure. It does not access persistence or decide step order.
- `HubSpotCRMAdapter.execute(order_id, step)` reads the approved order and needed M9B receipt IDs in a short session, closes/rolls it back before any provider call, and returns only the matching existing `HubSpotCompanyReceipt`, `HubSpotDealReceipt`, `HubSpotAssociationReceipt`, or `OrderSyncStepFailure`.
- The adapter may read the trusted Odoo customer for a Company name through the already-composed `BusinessDataProvider`, using the exact order `customer_reference` and no product SKUs. Exactly one returned candidate with the exact trusted reference is required. M9C already applied active-customer policy before creating the approved Odoo order; M9D does not re-run that policy after the durable Odoo receipt. The Company name and stable reference originate from Odoo; neither HubSpot data nor Gmail/extraction identity is trusted. This Odoo read plus the Company request shares the existing 15-second M9B `HUBSPOT_COMPANY` executor allowance; no call receives a fresh aggregate budget. If the selected environment cannot complete inside the current allowance, report the concrete mismatch instead of silently extending M9B timing.
- The adapter is read-only with respect to OpsFlow. It never changes `order_syncs`, checkpoints, receipts, claim fields, order state, or audit rows. The M9B coordinator persists returned receipts/failures under its current claim fence.
- The provider base host is fixed to HubSpot's official API host. Task 1 live-verified the fixed Company, Deal, unique-search, association, and association-read routes and exact observed request/result contracts below. Production code uses one centralized `HUBSPOT_API_VERSION = "2026-09"` constant; route paths are fixed code constants, never settings. Never accept arbitrary model/object names, properties, route fragments, or user-supplied URLs.
- Runtime authentication is `Authorization: Bearer <OPSFLOW_HUBSPOT_SERVICE_KEY>`. HubSpot Service Key settings were human-verified to show exactly `crm.objects.companies.read`, `crm.objects.companies.write`, `crm.objects.deals.read`, and `crm.objects.deals.write`; controlled Company, Deal, and association writes all succeeded with that key. No distinct association permission was required in this portal. No schema/property-write grant belongs on the runtime key. Schema creation/verification, portal validation configuration, and pipeline/stage setup use a separate setup/admin identity or manual account setup.
- Wrong-account protection uses the verified read-only `GET /integrations/v1/me` contract, which returned portal ID `149461984`, account type `DEVELOPER_TEST`, and currency `USD` for the configured Service Key. Runtime composition must require `OPSFLOW_HUBSPOT_EXPECTED_PORTAL_ID=149461984` and verify the returned `portalId` before writes. Wrong portal and identity-endpoint 401/403 map to `INTEGRATION_CONFIG`; 429 retains `PROVIDER_RATE_LIMIT` and a valid bounded delay; network/timeout/5xx retain `PROVIDER_UNAVAILABLE`; malformed successful identity JSON maps to `PROVIDER_INVALID_RESPONSE`. This is an identity endpoint only; CRM operations remain on the date-based API. Do not add legacy OAuth/private-app authentication to obtain metadata.

### Company

- Stable upsert/lookup identity: unique Company property `opsflow_customer_reference_v2`, sourced exactly from trusted Odoo `res.partner.ref`. Its setup definition is internal name `opsflow_customer_reference_v2`, string/text type, label `OpsFlow Customer Reference v2`, and `hasUniqueValue=true`.
- Managed properties: built-in `name` from the current trusted Odoo partner name and `opsflow_customer_reference_v2`. An upsert may create the Company if absent and may restore/update only these two OpsFlow-managed properties on the record selected by the unique key; it must not synchronize domain, address, phone, industry, owner, Contact associations, or any other human-managed field.
- Exact success is one terminal, successful result for that stable reference with one confirmed provider record ID returned as `HubSpotCompanyReceipt.company_id`. Missing or mismatched identity, duplicate/ambiguous results, or malformed IDs yield no receipt and a bounded failure.
- If an upsert finds the same unique reference but the managed `name` differs, Odoo remains authoritative and the upsert may update only that managed name. A result whose stable reference differs, multiple results for the key, or evidence that the unique property is not unique is a bounded identity/reconciliation conflict; never create a second Company under a different key.

### Deal

- Stable create/read/update identity: unique Deal property `opsflow_order_id`, the canonical lowercase OpsFlow order UUID. Its setup definition is internal name `opsflow_order_id`, string/text type, label `OpsFlow Order ID`, and `hasUniqueValue=true`.
- Managed properties only: `dealname` derived deterministically from approved PO number and a short order-ID suffix, truncated at a project cap of 128 characters after confirming the account accepts it; `amount` computed as `sum(line.quantity * line.submitted_price for approved order lines)` using `Decimal` only, before tax, then serialized with `format(total, "f")` as a plain fixed-point decimal string with no exponent, quantization, or additional rounding; configured `pipeline` and initial `dealstage` IDs; `opsflow_currency` from the approved ISO currency; `opsflow_po_number`; and `opsflow_order_id`. Do not truncate or transform the trusted Company name; if it violates the verified provider property limit, return a bounded rejection without receipt.
- Require the order currency to equal configured `hubspot_portal_currency`. Do not calculate from Odoo `amount_total`, convert currency, use float arithmetic, apply a separate HubSpot rounding policy, or sync other fields. A genuinely absent Deal is created with `POST /crm/objects/2026-09/0-3` and the full managed create payload, including initial `dealstage`. Existing records are updated only by provider ID with `PATCH /crm/objects/2026-09/0-3/{dealId}`; every such update omits `dealstage` and `pipeline`. If a matching in-progress Deal has already moved from the configured initial stage, treat it as `RECONCILIATION_REQUIRED` and do not write. This is the exception path for an unexpected human mutation before sync completion. After `COMPLETED`, Phase 9 does not sync the Deal again.
- A receipt requires exactly one terminal successful result correlated to the submitted OpsFlow UUID and one confirmed opaque provider record ID returned as `HubSpotDealReceipt.deal_id`.
- For an existing record found by the exact `opsflow_order_id` search, read the provider ID, identity, pipeline, and current stage. If the stage is not the configured initial stage, return `RECONCILIATION_REQUIRED` without mutation. Otherwise PATCH by the exact provider ID, with only the approved OpsFlow-owned mutable fields and never `dealstage` or `pipeline`; reread the record and issue a receipt only if ID/identity/pipeline/stage remain valid. A unique-key create conflict after an empty search maps to retryable `PROVIDER_UNAVAILABLE` only when it matches the provider-verified exact `opsflow_order_id` validation conflict; the next M9B invocation starts a fresh request and reconciles by identity. Other validation failures remain `PROVIDER_REJECTED`. A stable UUID with materially conflicting identity/payload is `IDEMPOTENCY_CONFLICT`; an ambiguous/unrecognizable provider record or state that cannot safely be reconciled despite valid identity is `RECONCILIATION_REQUIRED`. Do not create a replacement Deal or update unmanaged properties.

Task 1 verified the default `PUT` route and type `341`. Return `HubSpotAssociationReceipt(confirmed_at=UTC timestamp)` only after provider-confirmed success.
- Association occurs only after durable Company and Deal receipts. It adds no Contact or other object/relationship.
